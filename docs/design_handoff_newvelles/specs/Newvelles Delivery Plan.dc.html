Newvelles · delivery plan · two repositories, one contract

How to build this without the two repos blocking each other

The build spec says what to make. This says in what order, which repository owns each piece, and how the front end gets built before the backend produces real data. It also settles the LLM question, which is the one genuinely new external dependency in the project.

1 · The rule that makes two repos work

You have newvelles (Python, Lambda, produces JSON) and newvelles_web (JS, reads JSON). They only ever meet at a file in a public S3 bucket. So the coordination mechanism is not a process, it's an artifact:

Write stories.json by hand first. Before either repo changes, produce one realistic fixture — 30-odd stories, real headlines from a stored fetch, every field populated. Commit it to both repos: as test/fixtures/stories_v0.3.0.json in the backend and data/fixtures/stories_v0.3.0.json in the front end. The backend's job becomes "produce a file that validates like this one." The front end's job becomes "render this file." Neither waits for the other.

That fixture is what turns a sequential project into a parallel one. It costs an afternoon, and it's the single highest-leverage thing on this plan. The mockups already encode the shape — the prototype's STORIES array is effectively a hand-written fixture, so lifting it into JSON is mechanical.

Versioning

Put "version": "0.3.0" at the top of both new files and have the front end refuse to render an unrecognised major version, logging loudly instead of failing silently. When the schema changes, the JSON schema file in newvelles/schemas/ is the source of truth and the fixture is regenerated from a real run, not edited by hand.

2 · The LLM decision

This is the only piece needing a new account, key or bill, and the volume is so small that the interesting question isn't price — it's what you have to operate.

What the workload actually is

Roughly 600 input tokens (a dozen headlines plus the instructions) and 20 output tokens (one sentence) per story. With fingerprint caching, 30–60 new namings a day, so about 1,500 calls and under a million tokens a month. That is a rounding error at every price point below.

Decided: Bedrock-hosted Haiku, behind a provider interface. The eighty-cent monthly difference against GPT Nano was not worth a decision; the operational difference was. Compute already runs in AWS with an IAM role, so Bedrock means no secret in the Lambda environment, no key rotation, no second invoice, and no new account to reason about when something breaks at 6am. The interface below stays in place regardless — if Bedrock model access is slow to enable in your region, ship phase 2 on the OpenAI account as a stopgap by changing one environment variable, rather than waiting on an access request.

Write it as an interface, not a call

Ten lines that keep the decision reversible. This is the only place in the codebase that knows which vendor you chose:

First step, before any code: Bedrock model access is per-account and per-region, and it is not on by default. Request access to anthropic.claude-haiku-4-5 in the Bedrock console for the region your Lambda runs in, then add bedrock:InvokeModel for that model ARN to the Lambda execution role. Approval is usually quick, but it is the one item here with an external wait, so file it today and build the rest while it clears.

# newvelles/models/naming.py

def _name_via_bedrock(prompt: str) -> str: ...
def _name_via_anthropic(prompt: str) -> str: ...
def _name_via_openai(prompt: str) -> str: ...
def _name_via_local(headlines) -> str: ...      # spaCy fallback, no network

PROVIDERS = {
    "bedrock":   _name_via_bedrock,
    "anthropic": _name_via_anthropic,
    "openai":    _name_via_openai,
    "local":     _name_via_local,
}

def name_story(story) -> tuple[str, str]:
    """Returns (headline, headline_source)."""
    provider = os.environ.get("NEWVELLES_NAMING_PROVIDER", "local")
    try:
        return PROVIDERS[provider](build_prompt(story)), provider
    except Exception as e:
        log.warning("naming failed (%s), falling back: %s", provider, e)
        return best_real_headline(story), "fallback"

Three consequences worth naming. The default is local, so a missing configuration degrades instead of breaking. headline_source travels into stories.json, so you can see in the data — and in monitoring — how many stories were named by the model versus the fallback. And the local provider is a real implementation, not a stub, which means phase 1 can ship with readable names before any vendor decision is made at all.

Environment variables to add

NEWVELLES_NAMING_PROVIDER   bedrock | anthropic | openai | local   (default: local)
NEWVELLES_NAMING_MODEL      e.g. anthropic.claude-haiku-4-5-v1:0
NEWVELLES_NAMING_TIMEOUT    seconds per call, default 8
BEDROCK_REGION              only for bedrock; defaults to the Lambda's region
ANTHROPIC_API_KEY           only for anthropic
OPENAI_API_KEY              only for openai

Document all of them in docs/ENVIRONMENT.md — the repo's own convention, and the thing most likely to be skipped under time pressure.

Cost guardrail: whichever vendor, set a hard monthly budget alert at $10 and cap the per-run naming count (say 60) so a clustering bug that produces 900 tiny stories can't produce 900 calls. The cap is three lines and it's the only realistic runaway path in this design.

3 · Milestones

Six milestones. Each has one owning repo, an explicit dependency, and a definition of done you can check without asking anyone.

M5Point the front end at the real buckets; cut overnewvelles_webM1–M4Site reads production stories.json + momentum.json; old page still reachable until you're happy

Where the parallelism is

M2 depends only on M0. That's the point of the fixture: the entire front end can be built while the backend is still merging clusters, and the two only meet at M5. If you're working alone, M2 is also the pleasant work to do while a threshold sweep runs.

What must be sequential

M4 needs M1's stable story ids, because momentum is meaningless if identity churns between runs. M3 and M4 are independent of each other and can land in either order — if the vendor decision drags, do M4 first.

4 · Coordination mechanics

Order of operations at every cutover

Producer before consumer, always. The backend publishes a new field, the field sits unused in the bucket for a run or two, and only then does the front end start reading it. Never the reverse — the front end must never ship code that requires a field the pipeline doesn't yet write.

Use the QA bucket as the staging contract

The repo already has environment-aware buckets and make qa-invoke / make qa-check-s3. Have the front end read from an environment variable for the bucket base URL so the same build can point at QA or production. Then "does the new front end work with the new pipeline?" is answerable before anything touches the live site.

Feature flags, not branches

Both repos should stay on short-lived branches merged to main frequently, with behaviour gated by flags: NEWVELLES_NAMING_PROVIDER=local keeps naming off, and a front-end flag chooses fixture versus live data. Long-lived feature branches across two repos that must agree on a schema is how a solo project stalls.

Keep the old file until the new site is live

latest_news.json keeps being written, unchanged, through all six milestones. It costs one extra upload per run and it means the current site never breaks while the new one is built. Delete it only once the new front end has been live and stable for a couple of weeks.

Monitoring additions

There's already a monitoring dashboard reading from S3. Four numbers per run are worth adding, because each one catches a specific failure that is otherwise invisible:

  • Story count — catches a merge threshold gone wrong. A jump to 150 or a drop to 6 is a bug, not a news day.
  • Fallback naming count — catches a silent API outage.
  • Unmapped feed count — catches a new feed nobody added to the source table.
  • Stories with carried ids — catches identity churn breaking momentum.

5 · A realistic solo sequence

If this is evenings and weekends, in this order, with each step leaving the project in a working state:

  1. Threshold sweep and fixture (M0). Half a day on the sweep, an afternoon on the fixture. Ends with a number you trust and a file both repos can build against.
  2. Backend merge + sources (M1). The biggest single improvement in the project, and no new dependencies. The old site keeps running throughout.
  3. Front-end board + wire (M2). Satisfying, self-contained, and you already have the prototype as a reference implementation.
  4. Momentum (M4). Do this before naming if the vendor decision isn't settled — it has no external dependency and it's what makes the design feel alive.
  5. Naming (M3). Enable in QA, watch the names for a few days against real clusters, then production. The prompt will need a couple of rounds of tuning; budget for that rather than expecting the first version to be right.
  6. Cut over (M5). New site at the root, old page kept at a path for a fortnight.

7 · Open items

  • The vendor call — settled: Bedrock. Remaining action is the model access request plus the IAM policy on the Lambda role.
  • Run frequency — settled: unchanged at rate(6 hours), four runs a day. The momentum datapoint for a day is the peak outlet count across that day's four runs; see the build spec.
  • Naming stability rule. Rename a story only when its article set has grown by more than 50% since the naming that produced the current headline. Needs confirming before M3 — at four runs a day the alternative is a headline that changes up to four times while someone is reading.
  • The fixture — done. stories_v0.3.0.json and momentum_v0.3.0.json are built from a real fetch, with a README recording every derivation rule and the known limits of the momentum approximation.

8 · Local end-to-end, and what happens when it goes wrong

Running the whole thing on a laptop, Haiku included

Confirmed, with one caveat. The CLI already runs the full pipeline without AWS: newvelles --rss_file data/rss_source_short.txt fetches, clusters, and — through log_visualization() — writes ./latest_news.json, /tmp/newvelles/latest_news.json and a timestamped copy under /tmp/newvelles/logs/. The --s3 flag is opt-in, so a local run touches no bucket.

Bedrock does not change that. It is an ordinary boto3 client, so it authenticates from the same credentials .env.local already carries — no Lambda, no container, no deploy. A full local run with naming enabled costs roughly three cents at 40 stories.

Two things to build so local runs stay pleasant:

  • A local naming cache path. The cache lives in the private bucket in production; point it at ./cache/story_names.json locally via NEWVELLES_NAMING_CACHE, or every dev run re-pays for names and needs S3 to work at all.
  • An offline mode that is genuinely offline. NEWVELLES_NAMING_PROVIDER=local — the spaCy fallback — must run with no credentials and no network beyond RSS. That is the default, so a fresh clone works before anyone has Bedrock access.
One refactor to do first. log_visualization() (CLI) and log_s3() (Lambda) are separate functions that already duplicate their upload logic and have already drifted — the Lambda path omits the latest_log_reference field the CLI path writes. Adding two more output files to both will make that worse. Collapse them into one emit function with a writer strategy (local, S3, or both) before M1 adds files, not after.

The old files keep being written

Yes — latest_news.json and latest_news_metadata.json continue exactly as they are, on schema 0.2.1, through every milestone. stories.json and momentum.json are additional objects, not replacements, and carry their own 0.3.0 version field. The existing site keeps reading the file it reads today and cannot be affected by the new pipeline stages, because they append rather than modify.

Versioning: what you have, and the two gaps

LayerStatusDetail
Code / deploymentSolidTimestamped ECR image tags, make list-prod-images, make rollback-prod with EventBridge pause, grace period, test invocation and auto-resume on failure
Data archiveSolidEvery run uploads newvelles_visualization_<version>_<datetime>.json to the private bucket. That is the 2021-onward history, and it is what momentum backfills from.
Schema versionPresentVISUALIZATION_VERSION in every archive filename, plus latest_news_metadata.json carrying datetime and version
Public file historyMissingS3 bucket versioning is not enabled anywhere in the repo. latest_news.json is overwritten in place on every run — the previous public file is simply gone.
Data restore pathMissingThere is no make restore-data. Rolling back the Lambda image does not fix a bad file already published; the site keeps serving it until the next scheduled run succeeds.

So the honest answer to "can we go back": you can roll back the code in a few minutes with a well-built, well-documented tool. You cannot currently roll back the data, and with four runs a day a bad publish is visible on the site for up to six hours. Three additions close that, none of them large:

  1. Enable S3 versioning on the public bucket, with a lifecycle rule expiring noncurrent versions after 30 days. At these file sizes the cost is negligible, and it makes any bad publish reversible with one aws s3api call instead of a hunt through the archive.
  2. Add make restore-data TIMESTAMP=... — copy a timestamped archive object from the private bucket over the public latest_news.json, and pause EventBridge so the next run doesn't immediately overwrite the restore. Ten lines of shell, and it belongs next to rollback-prod in the same guide.
  3. Add a pre-publish sanity gate. Schema validation passes happily on a run that produced three stories or four hundred; both are bugs, not news days. Refuse to publish when story count deviates more than 60% from the previous run or article count falls below a floor — log loudly and leave the old file in place. This is the guard that means you rarely need the other two.

Also worth fixing while in there: log_s3() writes metadata without latest_log_reference, so nothing in the public bucket records which archive object the live file came from. One line, and it turns a restore from a search into a lookup.

Recommended order: the sanity gate and the metadata reference land with M1, since M1 is the first release that can change the story count. Bucket versioning and restore-data can be done any time — but do them before M5, the cutover, which is the moment a bad publish would be most visible.
