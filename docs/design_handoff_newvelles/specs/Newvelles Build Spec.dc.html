Newvelles · implementation spec · draft for review

From 179 groupings to 34 named stories

What the backend has to produce for the redesigned front page to work, in four independently shippable phases. Nothing here changes the RSS ingestion, the TF-IDF clustering, or the Lambda deployment path. The work is a post-processing stage between build_visualization() and log_s3(), plus one new rollup file.

1 · Where the new code goes

Today handler.py runs three steps: build data from RSS, build_visualization(), log_s3(). The redesign inserts one stage in the middle and one after:

title_data        = build_data_from_rss_feeds(RSS_FILE)
visualization, _  = build_visualization(title_data, cluster_limit=...)

# NEW — newvelles/models/stories.py
stories           = build_stories(visualization)        # merge + resolve sources
stories           = name_stories(stories)               # LLM titles, cached

# NEW — newvelles/models/momentum.py
momentum          = update_momentum(stories)            # reads/writes rolling state

log_s3(visualization, stories=stories, momentum=momentum)

Five new modules, all pure functions except the two that touch S3 and the LLM:

FileResponsibility
models/stories.pyMerge overlapping groups into stories; compute outlet counts
models/naming.pyLLM headline generation with fingerprint cache and fallback
models/momentum.pyStory identity across days; rolling 14-day series
utils/sources.pyRSS feed URL → outlet name and domain
feed/log.pyExtended: two more public-bucket uploads

2 · Stage A — merging groups into stories

This is the change that does the most work for the least cost, and it needs no LLM. In the 16 August sample, the Alaska summit occupies at least twelve top-level groupings and the BBC video "Watch: Moment Trump and Putin meet in Alaska" appears in eight of them. The clustering isn't wrong — the two-level greedy pass legitimately puts one article in several groups. The output just never collapses them.

Article identity

Use the link field, normalised: strip query strings except where they carry the path (BBC appends ?at_medium=RSS; drop it), lowercase the host, drop www., drop trailing slashes. Two entries with the same normalised link are the same article. Title-based identity is unreliable — the same story reruns with edited headlines.

Merge rule

Build a graph over top-level groupings: an edge exists when two groupings share articles above a threshold. Connected components become stories.

def overlap(g1_links, g2_links):
    inter = len(g1_links & g2_links)
    return inter / min(len(g1_links), len(g2_links))

# edge when overlap >= MERGE_THRESHOLD (start at 0.5)
# connected components via union-find -> one story per component

Containment (min in the denominator) rather than Jaccard matters here: a four-article grouping fully contained in a thirty-article one should merge, and Jaccard would score that pair at 0.13 and leave them apart.

Tuning: 0.5 is a starting point, not a finding. Run it over thirty stored days from the private bucket and check the story count lands in the 25–45 band on a normal day. Too low and the summit swallows unrelated Trump stories; too high and you keep four Alaska piles. This is a half day of work with the archive you already have, and it's worth doing before anything else.

Outlet counting

The redesign ranks by distinct outlets, not article count — that's what stops twenty Yahoo reposts outranking a story the BBC, NYT and Politico all covered independently. The RSS source field is a feed URL, so it needs resolving:

https://feeds.bbci.co.uk/news/world/us_and_canada/rss.xml  ->  BBC       bbc.com
https://rss.nytimes.com/services/xml/rss/nyt/HomePage.xml  ->  NYT       nytimes.com
https://rss.politico.com/congress.xml                      ->  Politico  politico.com
https://www.yahoo.com/news/rss                             ->  Yahoo     yahoo.com

84 feeds map to far fewer outlets — several NYT and Politico feeds each. A static table in data/sources.json keyed by feed URL, with {"outlet", "domain", "section"}, is the whole implementation. data/rss_titles.json already holds part of this. Unmapped feeds fall back to the registered domain of the feed URL, and the run logs them so the table can be filled in.

2.5 · Stage A.5 — roundups, templates and kind

Running the merge over real fetches turned up a failure the spec's first draft didn't account for, and no amount of LLM naming fixes it: some clusters are held together by shared headline scaffolding rather than a shared subject. Real examples from the 9 August fetch, each currently a single "story":

Select Water Solutions Q2 Earnings Call Highlights
Essential Utilities Q2 Earnings Call Highlights
Watts Water Technologies Q2 Earnings Call Highlights
Warby Parker Q2 Earnings Call Highlights          <- four unrelated companies

Five Hacks Every Amazfit Balance 3 User Should Know
Five Hacks Every Amazfit Cheetah 2 Ultra User Should Know
10 Screenshot Hacks Every Mac User Should Know    <- one outlet's article series

This 27-Inch Asus OLED Gaming Monitor Is $120 Off Right Now
This LG Ultrawide OLED Gaming Monitor Is $200 Off Right Now
This 45-Inch LG UltraGear OLED Curved Monitor Is $700 Off  <- affiliate deals

TF-IDF cannot distinguish a template from a topic — the shared words are genuinely shared. Naming such a cluster produces a fluent headline for something that was never one event. The cluster is wrong upstream of the name.

The check

Two signals, both cheap, applied after merging and before naming:

  • Single-outlet: every article in the cluster comes from one outlet. A real event gets covered by several; an article series does not.
  • Shared template run: the longest contiguous word run appearing in 60% or more of the titles. Three or more words means the titles came from a template. Contiguity matters — loose word overlap flags real stories, because three articles about one primary election naturally share "primary", "win" and a candidate name without being a template.
def classify(story):
    if majority_match(story.titles, DEAL_RE):   # "$120 Off", "% Off", "Preorder", "Deal"
        return "deal"
    if story.outlet_count == 1 and template_run(story.titles) >= 3:
        return "roundup"
    return "story"

def template_run(titles):
    """Longest contiguous word run shared by >=60% of titles,
    excluding runs that contain a proper noun."""
    # A run carrying a proper noun is a subject, not a template:
    # "dispense $600M for vaccines RFK Jr. held up" is two outlets
    # covering one event, not a headline pattern.

One trap worth knowing before you implement this. Detecting proper nouns by capitalisation fails on title-case headlines, where every significant word is capitalised — Lifehacker and Yahoo Finance both write that way, and they are exactly the feeds that produce templates. Collect the proper-noun set only from sentence-case titles, and treat weekday and month names as generic (the daily rate and price roundups are built on them). Run against the 9 August fetch, the rule gives:

story    24     multi-outlet coverage, plus single-outlet news
roundup   7     earnings-call highlights, "Hacks Every X User Should Know",
                insider-filing series, daily metals/crypto prices
deal     10     price-off posts, preorder offers, deals live blogs

No genuine news cluster is misclassified at that setting, which is the failure that matters — a roundup shown as a story is a mild embarrassment, a real story buried under a roundup filter is a bug. Two known misses in the other direction: a movie-recommendation series and the daily CD/mortgage rate posts still read as stories. Both are single-outlet, so they sit low in an outlet-count ranking anyway.

Emit the result as kind on every story. Nothing is discarded — classification, not filtering, because a deals reader may well want the deals; they just shouldn't outrank a foreign-policy story on the front page.

Why this matters more than it looks: in the QA feed set, commerce and article-series clusters outnumber news clusters. A front page ranked purely by outlet count would put "This Anker Charging Station Is 30% Off" alongside Gaza ceasefire coverage. The board view should show kind == "story" only, with deals and roundups reachable behind a filter pill.

The second deduplication axis

Related finding from the same sweep. In data/latest_news_example.json, 410 article entries resolve to 121 unique links — but no article appears in more than one top-level group. The duplication is entirely within a group, across sub-groups: one article shows up in as many as 16 sub-groupings of the same parent. Flattening a story to a single list of articles removes all of it, with no threshold and no tuning. Stage A's merge handles cross-group duplication, which is a production-scale phenomenon; this handles the intra-group kind, which is present at every scale.

Consequence for the threshold sweep: run it on stored production files (84 feeds). In the 12-feed QA set no article appears in two top-level groups at all, so the merge is a no-op there and any threshold looks equally correct. Testing the merge against QA data would tell you nothing.

3 · Stage B — LLM-generated headlines

Group identifiers today come from extract_common_substrings(), which is why they read as [next time] [no ceasefire] [6 takeaways]. Those are the longest shared substrings across headlines, and shared substrings are not topics. Keep them — they become the keyword pills, and they're good at that. The story name becomes a generated sentence.

Call shape

One call per story per run, cached. Batching all stories into one call is cheaper but couples failures together and makes the cache useless, so keep it one story per call.

DecisionRecommendation
ModelClaude Haiku — naming from headlines is not a frontier task, and latency matters inside a Lambda
InputUp to 12 headlines from the story, longest first, plus outlet names
OutputOne sentence, 6–12 words, sentence case, no trailing period
Timeout8s per call, 2 retries, then fall back
Concurrency4 parallel calls via ThreadPoolExecutor — 34 stories in ~15s
CredentialANTHROPIC_API_KEY from Lambda environment; document in docs/ENVIRONMENT.md

Prompt

You name news stories. You will get headlines that all cover the same
event, from different outlets.

Write one plain sentence naming what happened. Rules:
- 6 to 12 words, sentence case, no trailing period
- State the event, not the framing. Never adopt one outlet's angle.
- No clickbait, no questions, no colons, no "here's what"
- Use the names of people, places and organisations that appear
- If the headlines disagree about what happened, name the disputed
  fact, not one side's version

Headlines:
{numbered list of up to 12 headlines, each with its outlet}

Reply with the sentence and nothing else.

Against the sample cluster this should produce something close to "Trump and Putin meet in Alaska and leave without a ceasefire" — which is what the mockups use.

Cache

The Lambda runs every six hours and most stories persist between runs. Naming the same cluster repeatedly is wasted money and, worse, produces a headline that drifts between refreshes. Cache on a fingerprint of the story's content:

fingerprint = sha256(",".join(sorted(normalised_links)[:20]))

Store {fingerprint: headline} in a single story_names.json in the private bucket, loaded at the start of a run and rewritten at the end. When a story gains articles the fingerprint changes and it gets renamed — which is correct, since the story has moved on. Expect 30–60 real calls a day rather than several hundred.

Failure path

The naming stage must never fail a run. If the API is unreachable or the key is missing, fall back to the longest real headline in the story from the outlet with the most articles. That's the "best real headline" option from our earlier conversation, and it degrades gracefully — the site still reads sensibly, it just loses the neutral phrasing. Log the fallback count so a silent outage is visible in monitoring.

Cost: roughly 600 input and 30 output tokens per call, 30–60 calls a day. On Haiku pricing that's about a dollar a month, well inside the low-cost constraint. Set a monthly budget alert anyway.

4 · Stage C — momentum from the archive

The sparklines and "running 4 days" counters need one thing the current pipeline never produces: a story that knows it existed yesterday. The private bucket already holds every timestamped run back to 2021, so no new collection is needed — but querying that history at read time would mean infrastructure you don't have. Precompute instead.

Story identity across days

Links can't carry identity across days: tomorrow's coverage of the same story is entirely new articles. Match on content overlap instead, against yesterday's stories only:

def match_previous(story, previous_stories):
    best, best_score = None, 0
    for prev in previous_stories:
        score = jaccard(story.keywords | story.entities,
                        prev.keywords | prev.entities)
        if score > best_score:
            best, best_score = prev, score
    return best if best_score >= CARRY_THRESHOLD else None   # start at 0.4

A match inherits story_id and increments days_running; no match mints a new id. Keywords come free from the existing substring extraction. Entities need a spaCy NER pass — spaCy is already a dependency and already loaded from EFS, so this is a function call, not a new model.

The rollup file

One small file, rewritten every run, holding a rolling 14-day window. This is the whole "months of archive" story from the front end's point of view — the deep archive stays in the private bucket, unqueried, and the site reads a file measured in kilobytes.

// public bucket: momentum.json
{
  "generated": "2026-08-16T08:12:00",
  "window_days": 14,
  "stories": {
    "st_a91f2c": {
      "first_seen": "2026-08-10",
      "days_running": 4,
      "series": [
        {"date": "2026-08-13", "outlets": 5,  "articles": 9},
        {"date": "2026-08-14", "outlets": 13, "articles": 28},
        {"date": "2026-08-15", "outlets": 11, "articles": 24},
        {"date": "2026-08-16", "outlets": 14, "articles": 31}
      ],
      "peak_date": "2026-08-14",
      "trend": "cooling"
    }
  }
}

trend is derived, not stored per article: compare the last two days' outlet counts against the window mean and emit one of new, climbing, peaked, cooling, steady. The front end prints it verbatim under the sparkline ("peaked yesterday", "still climbing"), so the vocabulary is a contract — changing a label changes the UI copy.

Backfill: run the merge and identity passes over the last 14 days of stored runs once, offline, to seed momentum.json. Otherwise every story reads "new today" for the first fortnight and the sparkline column is empty at launch — the least convincing possible first impression.

Two deliberate changes from the current schema. Articles are a list, not an object keyed by title — the current shape can't hold two articles with identical titles, which happens with syndicated wire copy. And published is normalised to ISO 8601; the current file carries at least four RSS date formats ("Sat, 16 Aug 2025 18:51:12 +0000", "2025-08-16T04:31:19Z", and EST/GMT variants), which pushes parsing into the browser for no reason.

Section assignment

The mockups' section pills (World, US politics, Markets, Tech, Science, Local) don't exist in the data yet. Derive them from the feed, not the content: each entry in data/sources.json already needs a section, and a story takes the modal section of its articles. No classifier, no LLM call. It will be wrong occasionally, and that's acceptable for a filter pill.

Front-end changes

The board view shows kind == "story" only; roundups and deals stay reachable from a filter pill in the wire, so nothing is hidden but nothing commerce-shaped competes for the lead slot. The current app reads the three-level nesting directly in newsStore.js and ranks in rankGroupings.js. Against stories.json both get simpler: ranking moves to the backend (or becomes a one-line sort on outlet_count), and the drilldown collapses to one expand-in-place level. Search keeps working the way it does now — it just runs over story headlines, article titles, outlet names and keywords.

6 · Phasing

Each phase is shippable on its own and improves the current site even if the next one never lands.

PhaseShipsWhy this order
1Merge + source resolution → stories.json, no LLMRemoves the redundancy that makes the site feel like noise. Headlines are the best real headline. No new external dependency, no new cost. This alone gets you most of the way.
2LLM naming + cache + fallbackFixes the fragment tags. Isolated behind a feature flag and a fallback, so a bad day for the API is a cosmetic regression, not an outage.
3Momentum: identity, rollup, 14-day backfillNeeds stable story ids from phase 1 to be meaningful. Unlocks the sparkline column and the "running N days" line.
4New front end on stories.json + momentum.jsonBoard landing view, wire deep dive. Can start against a hand-written fixture the day phase 1's schema is agreed.

Deferred, in priority order

  • Entity filters. The NER pass from phase 3 already produces the entities; exposing them as first-class filters is mostly front-end work plus an entity index in stories.json.
  • Framing comparison. Needs no new data — two headlines from the same story on the same day, chosen for maximum lexical distance. A heuristic gets surprisingly far before any LLM is involved.
  • Barely-covered rail. Already computable from outlet_count; it's in the board mockup and needs no backend work at all.
  • Day navigation. Reading a past day means one more public file per day (stories/2026-08-15.json) written once and never updated. Cheap, but it multiplies the public bucket's object count, so decide on a retention window first.
  • Research domain. A separate corpus with its own weighting — venue, citation velocity, distinct groups working on a problem — rather than outlet count. Same shell, different ranking. Worth a spec of its own.

7 · Testing

Following the repo's stated philosophy — observable behaviour, real fixtures, mocks only at the network boundary:

  • Merge: fixture built from a production-feed file, asserting the twelve Alaska groupings collapse to one story and that the BBC video appears exactly once. Assert the total story count lands in the expected band. A QA-feed fixture cannot test this — no article appears in two top-level groups there.
  • Classification: the three real clusters quoted in section 2.5 as fixtures, asserting the earnings-call and hacks clusters classify as roundup, the monitor cluster as deal, and a genuine multi-outlet cluster as story. This is the test that stops a template cluster reaching the lead slot.
  • Source resolution: every feed in rss_source.txt resolves to a mapped outlet, or the test fails with the list of unmapped feeds. This is the test that keeps the table honest as feeds are added.
  • Naming: mock the API (it's an external service). Assert the cache prevents a second call for an unchanged fingerprint, that a changed fingerprint triggers one, and that a raised exception yields the fallback headline rather than propagating.
  • Momentum: two synthetic consecutive days where a story persists and another dies. Assert id carry-forward, days_running, and that the window never exceeds 14 entries.
  • Schemas: new JSON schemas for both files, validated in the existing S3 upload path alongside the current two.

8 · Open decisions

  1. Run frequency. Settled: unchanged at rate(6 hours) — four runs a day. Each run rewrites the current day's datapoint with max(existing, this run) on outlet count, so a day records its peak rather than whatever the 6am run happened to catch. Article counts follow the same rule. Only the current day is ever mutated; earlier days in the window are immutable once passed.
  2. Merge threshold. Needs the archive sweep described above before it's fixed in code.
  3. Naming stability. At four runs a day a story can be renamed up to four times, which is visible to anyone refreshing. Recommendation: rename only when the article set has grown by more than 50% since the naming that produced the current headline — store the article count alongside the cached name and compare. A story that gains two articles keeps its headline; one that doubles earns a new one. Worth confirming before phase 2 ships.
  4. Backfill depth. 14 days seeds the sparklines. Going deeper is cheap offline and would let the site say "biggest story since June", which is the kind of line the archive uniquely enables.
